# Android App Professionalization

## Professionalization

The Android app must be professionalized from a single-file reference implementation into a real, production-quality app, fixed properly and completely with no technical debt allowed anywhere. The Android app must address all gaps, technical debt, missing/incomplete/stubbed features across both iOS and Android. The Android app is not a dead shell but a mostly-working app with a few high-impact defects layered on top. The Android app is a thin renderer over a single Rust state machine via dispatch(HighlighterAppAction) + state() snapshot tree; iOS parity requires only rendering/IA/navigation work, not new business logic. The Android app's package ID is `com.highlighter.app`. The Android app must connect to relays for functionality. The Android app's UI panels must be organized into feature-scoped files rather than a single monolithic file. The entire UI is refactored from a single 3,317-line MainActivity.kt into 23 cohesive files organized by feature, with MainActivity.kt reduced to 64 lines and feature-specific panels organized under ui/ packages. Cross-file symbols use internal visibility while symbols used within a single file remain private. The app uses dark/light Material3 color schemes derived from the brand palette, with all 16 UI files using theme tokens and zero hardcoded color literals remaining outside the theme layer. The brand palette maps to Material3 tokens as: Paper→background, Ink→onSurface, Muted→onSurfaceVariant, Line→outline, Moss→primary, Gold→secondary, Clay→tertiary. The app has a proper adaptive vector launcher icon recreating the iOS quote-marks mark, including a monochrome layer for themed icons. System back navigation closes the innermost open overlay (comments → invite → room → article → profile → feedback thread) before exiting the app, with predictive back enabled. No deep-link handling exists in the app; the original onCreate only does enableEdgeToEdge() and setContent. FEEDBACK_PROJECT_COORDINATE lives in AppConfig.kt in the same package as MainActivity. The Android app includes a Settings screen with Network, Media, Library (Bookmarks/Feedback), What's New, and Sign-out sections. The app has unit tests for formatters (pure functions) as a seed test suite. Android podcast playback v1 uses a Media3/ExoPlayer podcast player with a mini-player bar and full listening screen with chapters/speed/skip, matching iOS's podcast functionality (waveform extraction excluded as platform-local). Account creation no longer bricks when the NIP-05 availability check fails; a failed check lets the user proceed (the claim is skipped), and a 30-second deadline plus HTTP timeouts are applied to the creation request. Android release builds must use R8 minification with resource shrinking, reducing APK size from 37 MB to 29 MB, ProGuard keep rules for JNA/UniFFI, optional signing via git-ignored keystore.properties, and property-driven versionName/versionCode. The Android Edit Profile is a full-screen destination with banner/avatar pickers dispatching UploadEditProfileImage, text fields for displayName/name/about/nip05/website/lud16, live upload spinners, error display, and SubmitEditProfile gated while busy. OCR capture is MISSING on Android — no CAMERA permission in the manifest, no camera integration, no OCR, and no ISBN entry/lookup (iOS has 15 capture files; Android has only a gallery-pick stub). The emulator has no camera, so the OCR flow must be validated via an injected image plus iOS reference. Comments on Android lack threaded replies (the core supports publishComment(parentEventId)), and search profile/community rows are non-tappable. Android cards must dispatch requestProfile, requestWebMetadata, requestIsbnPreview, and article hydration actions to achieve iOS parity for showing resolved author/cover/title on cards. The feed render path (UniFFI type mapping, enum/field names, state plumbing, core bridges) is byte-for-byte correct and symmetric with iOS; an empty feed is caused by data/auth/sync starvation at the core snapshot level, not a Compose/mapping bug. The parity plan is delivered at Plans/android-parity-plan.md and covers 38 validation-ready user flows, the Android gap audit (26 WORKING, 7 PARTIAL, 2 BROKEN, 3 MISSING), a UI/IA reorganization plan, a validation-harness plan, and a phased 8-phase roadmap (0–7). The remaining known gaps include: user-facing strings still hardcoded rather than in strings.xml, single ABI (arm64-v8a) only, dark theme deserves a visual once-over on emulator, podcast waveform/transcript views are iOS-only, naddr deep-link routing is TODO, App Links require server-side assetlinks.json deployment, and beta.highlighter.com/api/nip05 returns 404. All manual Refresh OutlinedButtons are removed from feed, rooms explorer, room detail/comments, reader, profile, bookmarks, settings, feedback, and room invite screens; pull-to-refresh gestures are retained.

A seeded test account with 16 followed highlighters and 115 confirmed kind:9802 highlight events exists at ~/Builds/test-account.txt, with nsec/npub/hex keys kept outside the git repo.

The validation harness (HighlighterTest AVD, adb, emulator, Maestro) is operational: APK installs, app launches, Compose nodes are discoverable by text/uiautomator for automation, and screenshots are capturable via adb.

The app exhibits frame-skip jank (200+ skipped frames) during navigation/refresh with block_on_local budget warnings for refresh_home_feed and refresh_room_detail, though no ANR was observed during the second validation run.
